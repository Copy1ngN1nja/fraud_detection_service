# Fraud Detection Service

DISCLAIMER

Сервис подготовлен в рамках выполнения домашнего задания в ШАД МТС 2026 по курсу ML-Ops.

## Что это за сервис и зачем он нужен

Это **real-time сервис детекции мошеннических транзакций**: транзакции поступают в
систему поштучно (событийно, через брокер сообщений), для каждой из них "на лету"
делается препроцессинг и скоринг заранее обученной моделью (LightGBM), результат
(скор мошенничества и предсказанный класс) сохраняется и становится доступен для
анализа. Помимо самого скоринга сервис непрерывно следит за качеством данных и
модели в проде: сравнивает свежие транзакции с историческими (adversarial
validation, PSI) и собирает операционные метрики (throughput, латентность, доля
фрода), которые визуализируются в Grafana.

Сценарий, под который спроектирован сервис: у вас есть обученная офлайн модель
скоринга транзакций, и нужно (1) прогонять через неё поток транзакций в реальном
времени, (2) хранить результаты, (3) видеть, не "поехали" ли данные/модель со
временем, без необходимости вручную сравнивать выгрузки.

## Из каких сервисов состоит система и на каких портах они работают

Всё поднимается одной командой через `docker-compose.yml` в корне репозитория.

| Сервис          | Порт (хост)  | Назначение                                                                 |
|-----------------|--------------|------------------------------------------------------------------------------|
| `interface`     | `8501`       | Web UI (Streamlit): загрузка транзакций/исторических данных, просмотр результатов |
| `fraud_detector`| `8010`       | Ядро сервиса: consumer из Kafka, препроцессинг, скоринг, adversarial-валидация. На порту (внутри сети — `8000`) отдаёт `/metrics` для Prometheus |
| `score_writer`  | `8011`       | Consumer из Kafka, пишет результаты скоринга в Postgres. На порту (внутри сети — `8001`) отдаёт `/metrics` для Prometheus |
| `postgres`      | `5434`       | Хранилище: скоринги, исторические данные, результаты adversarial-валидации (внутри Docker-сети — стандартный `5432`) |
| `kafka`         | `9095`       | Брокер сообщений (снаружи Docker-сети; внутри сети — `kafka:9092`)        |
| `zookeeper`     | `2181`       | Требуется для координации Kafka                                           |
| `kafka-setup`   | -            | Одноразовый служебный контейнер: создаёт топики `transactions` и `scoring` при старте |
| `kafka-ui`      | `8080`       | Web UI для просмотра топиков/сообщений Kafka                              |
| `prometheus`    | `9090`       | Сбор метрик с `fraud_detector`, `score_writer` и `node-exporter`          |
| `node-exporter` | `9100`       | Метрики хоста (CPU/RAM/диск/сеть) для Prometheus                          |
| `grafana`       | `3000`       | Дашборды поверх Postgres и Prometheus (логин/пароль — `admin`/`admin` по умолчанию, см. `.env`) |

> Порты `fraud_detector` (`8010`), `score_writer` (`8011`) и `postgres` (`5434`)
> на хосте намеренно не совпадают с портами по умолчанию (`8000`/`8001`/`5432`) —
> это сделано, чтобы не конфликтовать с локально установленным Postgres или
> другими проектами, использующими эти порты. Внутри Docker-сети сервисы
> по-прежнему обращаются друг к другу по стандартным портам (`postgres:5432`,
> `fraud_detector:8000`, `score_writer:8001`). Если конфликтов на вашей машине
> нет — можно вернуть маппинг `8000:8000`/`8001:8001`/`5432:5432` в
> `docker-compose.yml`.

## Что умеет сервис

- **Скоринг транзакций в реальном времени.** Транзакция приходит в Kafka-топик
  `transactions`, `fraud_detector` тут же её препроцессит и прогоняет через
  предобученную модель LightGBM, результат (score, prediction) уходит в топик
  `scoring` и оттуда сохраняется в Postgres.
- **Загрузка транзакций через веб-интерфейс.** `interface` (Streamlit) позволяет
  загрузить CSV с транзакциями и отправить их в Kafka построчно, с прогресс-баром.
- **Загрузка исторических данных для мониторинга дрейфа.** Отдельный блок в
  `interface` принимает CSV с историческими транзакциями, прогоняет их через тот
  же пайплайн препроцессинга (`preprocessing.py`) и сохраняет в Postgres — это
  baseline, с которым сравниваются свежие данные.
- **Adversarial validation (мониторинг дрейфа фичей).** Каждые 100 обработанных
  транзакций `fraud_detector` обучает классификатор "текущие данные vs.
  исторические" и считает ROC-AUC этого классификатора: чем ближе к 0.5, тем
  меньше дрейф, чем ближе к 1.0, тем сильнее данные "разъехались". Заодно
  вычисляются топ-3 признака, по которым классификатору проще всего отличить
  текущие данные от исторических (`feature_importance`).
- **PSI (Population Stability Index) скора модели.** В рамках того же раунда
  adversarial-валидации историческая выборка прогоняется через ту же модель
  скоринга, и считается PSI между распределением скора на исторических и на
  текущих данных — стандартная отраслевая метрика "уехал ли скор модели"
  (< 0.1 — стабильно, 0.1–0.25 — умеренный сдвиг, > 0.25 — значимый сдвиг).
- **Хранение результатов скоринга с разрезом по бизнес-полям.** В Postgres
  вместе со скором и предсказанием сохраняются "сырые" (не закодированные)
  `us_state`, `merch`, `cat_id` — чтобы дашборды могли фильтровать/группировать
  по ним.
- **Дашборды в Grafana** (провижинятся автоматически при старте, лежат в
  `grafana/dashboards/`):
  - **Adversarial Validation Monitoring** — heatmap ROC-AUC по времени, таблица
    топ-3 важных признаков (heatmap-style заливка по важности), timeseries PSI
    скора с пороговыми линиями.
  - **Live Scoring Monitoring** — плотность распределения скоров и TPS обработки
    транзакций, оба графика с фильтрами по `us_state` и `merch` (dropdown-переменные
    дашборда), плюс barchart средней доли фрода по `cat_id` за последние 1000
    транзакций.
  - **Fraud Detection Dashboard** / **Scoring Dashboard** / **Node Metrics** —
    операционные метрики из Prometheus: TPS, доля фрода, латентность обработки
    и записи в БД, метрики хоста (CPU/RAM/диск/сеть).
- **Аннотации в Grafana.** При каждом раунде adversarial-валидации сервис (если
  задан `GRAFANA_API_KEY`) ставит на дашборд аннотацию с текстом-саммари
  (ROC-AUC, PSI, топ признаки) — видно, когда именно произошёл раунд валидации.
- **Метрики Prometheus.** `fraud_detector` и `score_writer` отдают `/metrics`:
  время обработки транзакции, throughput, распределение скоров, доля фрода,
  время записи в БД. `node-exporter` добавляет метрики хоста.
- **Kafka UI** для отладки — можно посмотреть содержимое топиков `transactions`
  и `scoring` глазами, без консольных консьюмеров.

## Как это устроено (архитектура и поток данных)

Есть брокер сообщений **Kafka** с двумя топиками: `transactions` (сырые
транзакции на вход) и `scoring` (результаты скоринга на выход). Топики создаёт
одноразовый контейнер `kafka-setup` при первом старте.

1. **Отправка транзакции.** Пользователь загружает CSV в `interface`
   (Streamlit) и жмёт "Отправить". Interface читает файл построчно, генерирует
   `transaction_id` (UUID) для каждой строки и публикует в топик `transactions`
   сообщение вида `{"transaction_id": ..., "data": {...сырые поля транзакции...}}`.

2. **Препроцессинг и скоринг.** `fraud_detector` — Kafka consumer, читает
   `transactions` в цикле. Модель LightGBM (`scorer.py`) и `CatBoostEncoder`
   (`preprocessing.py`) загружаются с диска один раз при старте процесса, а не
   на каждое сообщение. Для каждого сообщения:
   - до препроцессинга запоминает "сырые" `us_state`, `merch`, `cat_id`
     (после препроцессинга они превращаются в числа — см. ниже);
   - гоняет строку через `preprocessing.py` (`run_preproc_row`) — версию
     препроцессинга, оптимизированную специально под построчную обработку
     (одна транзакция за раз), в отличие от `run_preproc`, рассчитанного на
     батч (см. пункт 5). Вместо операций над pandas DataFrame
     (`SimpleImputer.fit_transform`, `.apply(axis=1)`, `.astype` на весь
     фрейм) используются обычный `dict` и скалярная арифметика: импутация
     пропусков на выборке из одной строки не несёт статистического смысла
     (и вдобавок может уронить обработку сообщения при пропуске в
     каком-то поле — DataFrame из `SimpleImputer.fit_transform` в этом
     случае может потерять колонку), поэтому она убрана; временные признаки
     (год/месяц/день/час/минута из `transaction_time`) и геодистанция
     клиент-мерчант (формула гаверсинуса) считаются поштучно, без построения
     промежуточных Series/DataFrame;
   - кодирует категориальные признаки (`merch`, `cat_id`, `us_state` и
     другие, всего 8 колонок) не вызовом `CatBoostEncoder.transform()`
     напрямую — он на каждый вызов заново считает target-encoding по всему
     словарю обученных категорий (до ~1000 значений на колонку), даже если
     нужно закодировать одну-единственную строку, — а через плоские словари
     `{категория → закодированное значение}`, посчитанные один раз при
     старте сервиса по формуле `CatBoostEncoder` (`(sum + mean·a) / (count +
     a)`, глобальное среднее — для неизвестных категорий и категорий,
     встретившихся в трейне только один раз). Для одной транзакции это O(1)
     lookup по 8 словарям вместо пересчёта векторизованной формулы по всему
     словарю категорий на каждое сообщение;
   - логарифмирует `amount` и `population_city`;
   - скорит обработанную строку моделью LightGBM (`scorer.py`, порог
     классификации ≈ 0.494);
   - копит обработанную строку и её скор во внутреннем буфере (см. пункт 4);
   - публикует в топик `scoring` результат: `transaction_id`, `score`,
     `prediction`, а также сырые `us_state`/`merch`/`cat_id`.

3. **Запись в Postgres.** `score_writer` — второй Kafka consumer, читает топик
   `scoring` и построчно пишет результат в таблицу `scores` (создаётся сама при
   первом запуске, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` подтягивает новые
   колонки без потери данных при обновлении).

4. **Adversarial validation и PSI.** Модуль `feature_validator.py` внутри
   `fraud_detector` копит обработанные строки и их скоры. Как только накопилось
   100 штук, сам раунд валидации (обучение `LGBMClassifier`, запросы к
   Postgres, подсчёт PSI) выполняется не в потоке Kafka-consumer'а, а
   отправляется в фоновый поток (`ThreadPoolExecutor` с одним воркером) —
   иначе на время обучения (и это не доли секунды) consumer переставал бы
   вычитывать новые сообщения из топика `transactions`. `observe()` только
   копит буфер под локом и сразу возвращает управление; если следующий раунд
   накопится раньше, чем закончится предыдущий, он просто встанет в очередь
   на том же воркере (раунды не выполняются параллельно друг другу — это и не
   нужно, накопление буфера от этого не тормозится). Сам раунд:
   - весь батч сбрасывается в Postgres-таблицу `current_transactions`;
   - из таблицы `historical_transactions` (наполняется через `interface`,
     см. пункт 5) берётся случайная выборка того же размера;
   - на объединении current (метка 1) + historical (метка 0) обучается
     `LGBMClassifier`, отличающий их друг от друга — если получилось отличить
     хорошо (высокий ROC-AUC), значит данные заметно отличаются от baseline;
   - считается top-3 `feature_importance` этого классификатора — какие признаки
     сильнее всего "выдают" разницу;
   - историческая выборка прогоняется через боевую модель скоринга, и считается
     PSI между распределением скора на historical (baseline) и current (текущие);
   - всё это (`roc_auc`, топ-3 признака, `psi_target`) пишется в Postgres-таблицу
     `adversarial_validation_results`;
   - результат "отдаётся" в `visualizer.py`, который (если настроен
     `GRAFANA_API_KEY`) ставит аннотацию на дашборд Grafana через HTTP
     Annotations API.

5. **Исторические данные (baseline для дрейфа).** В `interface` есть отдельный
   загрузчик CSV с историческими транзакциями. Файл прогоняется через
   батчевый `run_preproc` (копия `preprocessing.py` лежит и в
   `fraud_detector/src`, и в `interface/src`, вместе с тем же `CatBoostEncoder`)
   и сохраняется в таблицу `historical_transactions` — именно её сэмплирует
   `feature_validator.py` на шаге 4. В отличие от `run_preproc_row` из пункта 2,
   здесь векторизованные pandas-операции (`SimpleImputer`, `.apply(axis=1)`,
   вызов `CatBoostEncoder.transform()` напрямую) — это уместный выбор: файл
   загружается целиком и обрабатывается один раз, а не построчно на каждое
   сообщение, поэтому построчная оптимизация из `run_preproc_row` здесь не
   нужна и не используется.

6. **Grafana** ничего не "пушит" ей активно (кроме необязательных аннотаций) —
   все дашборды при открытии сами ходят в Postgres (таблицы `scores`,
   `adversarial_validation_results`) и в Prometheus за метриками. Datasource'ы
   и дашборды провижинятся автоматически при старте контейнера из
   `grafana/provisioning` (конфиг) и `grafana/dashboards` (сами JSON дашбордов).

7. **Prometheus** параллельно, независимо от Postgres-пайплайна, каждую секунду
   скрейпит `/metrics` с `fraud_detector:8000`, `score_writer:8001` и
   `node-exporter:9100` — это операционные метрики (throughput, латентность,
   ресурсы хоста), не завязанные на бизнес-разрезы (`us_state`/`merch`/`cat_id`),
   для которых удобнее SQL по Postgres.

## Как всё это запустить

### Что должно быть предустановлено

- **Docker** (20.10+) и **Docker Compose v2** (команда `docker compose`, не
  устаревшая `docker-compose`) — всё остальное (Kafka, Postgres, Grafana,
  Python-окружения сервисов) поднимается внутри контейнеров, ставить руками не
  нужно.
- **Git** — чтобы склонировать репозиторий.
- Свободные порты на хосте: `2181, 3000, 5434, 8010, 8011, 8080, 8501, 9090,
  9095, 9100` — если что-то из этого уже занято локально (например, своим
  системным Postgres на `5432`, как это часто бывает), поменяйте маппинг
  портов в `docker-compose.yml`.
- Свободное место на диске: модель LightGBM и образы Kafka/Grafana/Prometheus
  в сумме тянут на несколько сотен МБ - пары ГБ свободного места достаточно.

### Пошагово

1. Склонируйте репозиторий на свою локальную машину:
   ```bash
   git clone <URL этого репозитория>
   cd fraud_detection_service
   ```

2. Создайте `.env` по аналогии с `.env.example` (лежит в корне репозитория):
   ```bash
   cp .env.example .env
   ```
   Значения по умолчанию в `.env.example` подходят для локального запуска "из
   коробки" (логины/пароли для Postgres и Grafana тестовые, менять не
   обязательно). При желании можно поменять `GRAFANA_ADMIN_USER` /
   `GRAFANA_ADMIN_PASSWORD`, а `GRAFANA_API_KEY` — опциональная переменная,
   нужна только для аннотаций adversarial-валидации на дашборде (см. раздел
   "Что умеет сервис"); без неё сервис работает штатно, просто без аннотаций.

3. Соберите образы и поднимите все сервисы:
   ```bash
   docker compose up -d --build
   ```
   Первый запуск займёт несколько минут: скачаются образы Kafka/Zookeeper/
   Postgres/Grafana/Prometheus, соберутся образы `fraud_detector`,
   `interface`, `score_writer` (внутри — установка Python-зависимостей).

4. Проверьте, что всё поднялось:
   ```bash
   docker compose ps
   ```
   Все сервисы должны быть в статусе `running` (для `kafka`, `postgres` — ещё и
   `healthy`; `kafka-setup` должен завершиться со статусом `exited (0)`, это
   нормально — он одноразовый). Логи конкретного сервиса:
   ```bash
   docker compose logs -f fraud_detector
   ```

5. Откройте нужные интерфейсы в браузере:
   - **http://localhost:8501** — веб-интерфейс: отправка транзакций в Kafka,
     загрузка исторических данных, просмотр последних фродовых транзакций.
   - **http://localhost:8080** — Kafka UI, посмотреть сообщения в топиках
     `transactions` / `scoring`.
   - **http://localhost:3000** — Grafana (логин/пароль из `.env`, по умолчанию
     `admin`/`admin`), дашборды лежат в папке "Fraud Detection".
   - **http://localhost:9090** — Prometheus (таргеты: Status -> Targets).

6. Прогоните тестовый сценарий:
   - В интерфейсе (`8501`) загрузите CSV с историческими транзакциями (формат
     как у `train.csv` из соревнования
     [teta-ml-1-2025](https://www.kaggle.com/competitions/teta-ml-1-2025)) —
     это создаст baseline для adversarial-валидации.
   - Загрузите CSV с транзакциями на скоринг (формат как `test.csv` из того же
     соревнования) и отправьте его в Kafka.
   - Смотрите результат: в интерфейсе — кнопка "Посмотреть результаты"; в
     Grafana — дашборды "Live Scoring Monitoring" (появится сразу же) и
     "Adversarial Validation Monitoring" (первая точка появится после того, как
     наберётся 100 обработанных транзакций).

7. Остановить сервисы:
   ```bash
   docker compose down
   ```
   Данные (Postgres, Grafana, Prometheus) сохранятся в Docker-volume между
   перезапусками. Чтобы стереть всё, включая накопленные данные, добавьте
   `-v`:
   ```bash
   docker compose down -v
   ```
